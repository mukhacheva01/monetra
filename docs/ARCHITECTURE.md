# Архитектура Monetra

## Архитектурная цель

Построить Monetra как `local-first` Flutter-приложение с модульной структурой, которое легко запустить как MVP и без боли развивать до синхронизации, backup и multi-device сценариев.

## Главные решения

### Клиентская часть

- `Flutter` для iOS и Android из одной кодовой базы
- `Material 3` с кастомной дизайн-системой, ориентированной на темную тему

### Управление состоянием

- `Riverpod`
- провайдеры на уровне фич
- разделение UI-состояния, бизнес-логики и слоя хранения данных

### Локальная база данных

- `Drift + SQLite`
- хороший выбор для структурированных финансовых записей, фильтров, агрегаций и месячной аналитики

### Синхронизация

- офлайн-first запись сначала в локальную базу
- отдельная очередь синхронизации для выгрузки на сервер
- разрешение конфликтов через `updatedAt` и версионирование записей
- рекомендуемый backend на следующем этапе: `Supabase`

## Слои приложения

```text
lib/
  app/         инициализация приложения, shell, theme
  core/        общие технические части: database, sync, constants
  features/    бизнес-модули
  shared/      переиспользуемые UI-компоненты
```

Когда модуль станет больше, его лучше развивать в такой форме:

```text
feature_name/
  application/   контроллеры, провайдеры, use cases
  domain/        сущности, value objects, контракты
  data/          репозитории, dto, local/remote source
  presentation/  экраны, виджеты, ui models
```

## Основные доменные сущности

- `TransactionEntry`
  - сумма
  - тип: расход или доход
  - `categoryId`
  - `accountId`
  - заметка
  - `createdAt`
  - `updatedAt`

- `Category`
  - название
  - иконка
  - цвет
  - тип категории

- `Budget`
  - месяц
  - `categoryId`
  - лимит
  - потрачено

- `Account`
  - название
  - валюта
  - баланс

- `SyncRecord`
  - тип сущности
  - id сущности
  - действие
  - payload
  - статус

## Поток данных

### Создание расхода

1. UI получает сумму, категорию, дату и заметку.
2. Экран вызывает контроллер фичи.
3. Контроллер валидирует данные и передает их в репозиторий.
4. Репозиторий сразу сохраняет запись в локальную базу.
5. Дашборд и аналитика обновляются из локальных данных.
6. Если синхронизация включена, sync manager помечает запись для отправки в облако.

## Почему local-first особенно важен

- расходы должны добавляться мгновенно
- приложением будут пользоваться в магазинах, транспорте и при плохом интернете
- графики и бюджеты должны открываться без ожидания ответа сервера
- синхронизация должна усиливать надежность, а не блокировать базовые сценарии

## Навигация

Рекомендуемая нижняя навигация:

- Dashboard
- Transactions
- Budgets
- Analytics
- Settings

Экран категорий можно разместить внутри блока Transactions или Settings в зависимости от финального UX.

## Направление дизайн-системы

- темная тема как основное состояние продукта
- контрастная типографика и понятная иерархия
- сдержанный, но заметный акцентный цвет
- компактные карточки для сводок и бюджетов
- палитра графиков, хорошо читаемая на темном фоне

## Стратегия тестирования

- unit-тесты для форматтеров, расчета бюджетов и агрегирования транзакций
- тесты репозиториев для локального слоя хранения
- widget-тесты для quick-add и основных состояний dashboard
- integration-тесты для сценариев создания, редактирования и удаления расходов

## Путь развития

### MVP

- только локальное хранение
- экспорт в CSV
- интерфейсы синхронизации уже описаны, но могут быть выключены

### V2

- авторизация
- зашифрованный backup
- облачная синхронизация
- восстановление на нескольких устройствах

### V3

- умные подсказки
- регулярные транзакции
- отслеживание подписок
- финансовые цели и прогнозирование
